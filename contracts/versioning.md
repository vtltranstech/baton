# Versioning contract - the central repo, the architecture of record, and the diagrams

Principle 4 (every artefact is a file in Git) is only true if someone commits. This contract says who commits what, when, and how a change to the architecture stays attributable to the story and feature that made it.

## 1. Branches and commit points in the central repo

- Every repo's default branch (`origin/HEAD`; `main` when there is no remote) is protected by the same `protect-main` hook as `main` and `master`, in the central repo and the service repos. Agents never commit to it. Every PR, central or code, targets the repo's default branch.
- Every story gets a central-repo branch `story/<F>-<S>` (`story/backlog-<S>` for a backlog story) created from the default branch by the first skill that writes for it (`/stories` or `/ready`). All of that story's artefacts are committed there.
- Commit points (the skill or agent that reaches the point commits; message format is fixed so the trace and the changelog can parse it):

| Point | By | Message |
| --- | --- | --- |
| stories drafted | `/stories` | `<S>: stories drafted (story-drafter)` |
| story written by a human | `/ready`, first time it sees the story | `<S>: story added (human)` |
| readiness result | `/ready` | `<S>: readiness n/9` |
| gate 1 | `/ready` after the PO's answer | `<S>: Ready (PO)` |
| design written | `/build` | `<S>: design (architect, <confidence>%)` or `<S>: findings (spike)` |
| design lenses | `/build` | `<S>: design lenses (<n> blocking)` |
| gate 2 | `/build` after the decision | `<S>: design approved (TL)` / `<S>: design changes requested (TL, round n)` / `<S>: auto-passed (light, <confidence>%)` / `<S>: blocked (TL)` |
| build done | `/build` | `<S>: build (developer) - sensors <green|red>` |
| diff shape + impact + mutation | `/build` | `<S>: diff shape, impact, mutation` |
| QA | `/build` | `<S>: QA PASS` / `<S>: QA FAIL loop n` |
| security | `/build` | `<S>: security <verdict>` |
| confidence + evidence | `/build` | `<S>: confidence <score> <lane>` |
| gate 3 | `/sprint-review` after the decision | `<S>: Approved (TL)` |
| documentation | `/ship` | `<S>: change note; promote architecture (+a elements, +r relationships, ~c changed)` |
| release | `/ship` | `<S>: trace regenerated; PR <url>` |
| archive | `/ship <F>` on `archive/<F>` | `<F>: archived (<n> stories)` |

- A commit touches only the story's artefacts plus the shared files the step legitimately changes (`docs/status.md`, `docs/metrics.md`, `docs/architecture/*`, `profile/domain.md` lines the PO approved, `profile/sensors/README.md`). A hook (`hooks/commit_scope.py`, W1) refuses a commit on `story/*` that touches another story's folders.
- Service repos: unchanged - branch `feature/<F>-<S>` per repo, one commit per task (`<S>: <task>`), PR opened by the release agent.

## 2. Shipping = one version

- `/ship` ends with the release agent opening the central-repo PR from `story/<F>-<S>` to the central repo's default branch and linking it from every code PR (each from `feature/<F>-<S>` to its repo's default branch) and vice versa. The Tech Lead merges code PRs and the docs PR in the same sitting (gate 3 is already theirs).
- On merge of the docs PR, CI (or the TL, by `baton tag <S>`) tags the default branch with `<S>`; when the feature's last story is Done, `baton tag <F>`. `baton tag` refuses on any other branch and when the tag exists. Tags are the versions: `git diff S-008..S-010 -- docs/architecture/workspace.dsl` is the architecture change between two shipped stories.
- Nothing is squashed: the branch's commit history is the audit trail of who decided what and when; the tag is the version.

## 3. The architecture of record stays attributable

- `docs/architecture/workspace.dsl` is the current model only. Its history is Git.
- `workspace.dsl` is generated by `baton c4` from the graph, never edited by hand. When the documentation agent promotes a story it runs `baton c4 --story <S>`, which stamps every **new** element and relationship, and every **changed** one, with Structurizr properties and a feature tag. Every later `baton c4` run carries all stamps over, and `baton c4 --check` ignores them, so a stamp is never drift:
  ```
  pricingComponent = component "PricingService" "..." "Spring @Service" {
      tags "F-002"
      properties {
          "baton.story" "S-010"
          "baton.feature" "F-002"
          "baton.since" "2026-11-05"
      }
  }
  orderService -> db "orders" "Mongo" {
      tags "F-002" "F-003"
      properties {
          "baton.story" "S-010"
          "baton.changed-by" "S-014"
      }
  }
  ```
  A later story that changes an element appends `"baton.changed-by" "<S>"` (comma-joined if several) and adds its feature tag; it never removes the original `baton.story`.
- A removed element is deleted from the model and recorded in `docs/architecture/CHANGELOG.md` with `removed-by <S>` so the history is not only in Git.
- `docs/architecture/CHANGELOG.md` gets one line per promotion, appended by `baton c4 --story <S>`, and removals go under `## Removed` as `| <date> | <element> | removed-by <S> |`: `| 2026-11-05 | F-002 | S-010 | +2 elements | +3 relationships | ~1 changed | 0 removed | changes/S-010.md |`.

## 4. Seeing the change (W5: `baton c4`)

| Command | Output |
| --- | --- |
| `baton c4 diff <refA> <refB>` (tags, shas or `main`) | `docs/architecture/changes/<refB>.md`: the delta rendered as a view - added elements and relationships green, changed orange, removed red (drawn from refA, dashed), unchanged grey; counts table; the raw DSL diff folded below. Exits 1 if the DSL at either ref does not validate. |
| `baton c4 feature <F>` | `docs/architecture/features/<F>.md`: a view containing every element tagged `<F>` plus their direct neighbours, colored New/Changed per `baton.story`; one dynamic view per story of the feature is listed under it (from the stories' candidate `.dsl` files, not from the workspace). |
| `baton c4 blame <identifier>` | prints `baton.story`, `baton.feature`, `baton.since`, `baton.changed-by` and the Git commits that touched the lines of that element. |
| `baton c4 --check` | unchanged: re-extracted edges vs the workspace; drift = exit 1. |

Rendering: `structurizr-cli export -format mermaid` when the CLI is present; otherwise the Mermaid is generated directly from the parsed DSL (the parser is W5's, shared with `c4`). The change note links the diff page; the trace page's architecture column embeds it.

## 5. What is NOT versioned this way

- `.baton/graph.sqlite` - derived cache, git-ignored, rebuilt from `profile/dependencies.yaml` by `baton graph load`.
- `docs/wiki/` - regenerated per module; history is Git, no tags.
- `docs/data-profile/` - current + previous only; a drift log line per run.
- Per-story artefacts after `Done` - moved to `docs/archive/<F>/<kind>/` by `/ship <F>` once the feature's last story has merged: on a branch `archive/<F>` cut from the default branch, because the last story's own branch does not hold the other stories' merged files and agents never merge. `baton trace` reads the archive and regenerates its links; agents never read the archive, `/retro` does.
